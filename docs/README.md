# Canonical Schema Strategy

## Problem Context
- Multiple organization-specific dataclasses mirror each partner's ingestion schema.
- Legacy datasets include helper/relationship tables (e.g., relation context, join tables) that should remain hidden from editors.
- Controlled vocabularies already exist in the data but are not surfaced uniformly.
- We must allow forms to create new records that remain compatible with every historical dataset.

## Guiding Principles
- **Single Canonical Model**: Define one set of neutral dataclasses that captures the shared semantics across all organizations.
- **Declarative Mappings**: Encode partner-specific quirks in mapping/adaptor layers rather than the canonical model itself.
- **Vocabulary-Driven Fields**: Resolve all controlled vocabularies explicitly (enums or tables) and reference them consistently.
- **Relationship Normalization**: Represent many-to-many and context tables as structured relationships in the canonical layer, expanding/collapsing them in adapters as needed.
- **UI-Friendly Exposure**: Keep canonical classes limited to the fields users should edit; technical linking state lives in the mapping layer.

## Recommended Process

### 1. Inventory Existing Schemas
- List every field, relationship, and auxiliary table for each organization's dataclass.
- Identify controlled vocabulary usage and free-text fields that should map to vocab terms.
- Mark fields as *required, optional, org-specific*, or *derived*.

### 2. Design Canonical Dataclasses
- Define shared base entities (e.g., Actor, Event, DigitalObject, Project).
- Introduce relationship structures such as `Relationship(source, target, type, role, context)` to cover relation-context tables.
- Use optional/variant typing (`Optional`, `Union`, or composition classes) to accommodate partner-only fields without polluting the core.
- Reference controlled vocabularies through enum fields or lookup IDs instead of raw strings.

### 3. Encode Controlled Vocabularies
- Promote existing implicit vocab values into explicit registries (enums, JSON/YAML definitions, or DB tables).
- Standardize serialization (e.g., store canonical IDs + display labels).
- Provide normalization rules for legacy free-text values to match vocab terms.

### 4. Build Mapping/Adapter Layer
- Implement bidirectional adapters:
  - **Partner → Canonical**: Translate partner dataclass instances to the canonical model, performing vocabulary normalization and relationship collapsing.
  - **Canonical → Partner**: Expand canonical objects into partner schema structures, recreating join tables and auxiliary records.
- Keep mapping definitions declarative (metadata maps, config files) to simplify onboarding future partners.

### 5. Update Form + Persistence Flow
- Generate forms from the canonical dataclasses so editors interact with a single schema.
- On save, run data through the canonical → partner adapter to persist in existing tables without breaking compatibility.
- For legacy imports, run partner → canonical conversion so downstream logic always works with the unified model.

### 6. Validation & Round-Trip Testing
- Test canonical round-trips for each organization to ensure no data loss:
  1. Partner record → canonical → partner should reproduce the original dataset.
  2. Canonical form submission → partner schema should satisfy all integrity constraints.
- Add regression tests covering controlled vocabulary normalization and relationship reconstruction.

## Implementation Tips
- Start with one complex organization as a pilot; refine adapters before rolling out to others.
- Store mapping metadata alongside dataclass definitions (e.g., `FieldMapping` descriptors) for discoverability.
- Consider versioning the canonical schema to manage future changes without breaking historical mappings.
- Document vocabulary sources and normalization rules so data stewards can maintain them.

## Expected Outcome
- Editors work with consistent forms aligned to a canonical schema.
- Controlled vocabularies are applied uniformly across all organizations.
- Existing datasets remain compatible through adapter-driven serialization.
- New partner schemas can be integrated by adding declarative mappings without altering the core model.

## Reference Implementation
- The canonical dataclasses live in `arkumu/projects/schema_manifest_canonical.py`.
- They are generated by inspecting all partner manifest dataclasses and merging fields that share the same canonical URI.
- Each field carries `metadata` with the canonical URI, a list of `SourceBinding` records (dataset + column per organization), and an `expose_in_forms` flag used by form builders.
- Helper utilities (`CANONICAL_CLASS_REGISTRY`, `get_canonical_class`) expose the classes by alias or canonical URI so adapter layers can look them up dynamically.
- Use the `property_bindings` metadata on each class when translating to organization-specific structures; it provides every dataset/column that needs to be populated.
- Translation utilities in `arkumu/projects/schema_adapters.py` provide `org_to_canonical()` and `canonical_to_org()` helpers for round-tripping data. They rely on the canonical metadata (`property_bindings`, `datasets_by_org`) so adapters automatically pick the correct columns per organization.

## Reproducing / Updating the Canonical Layer
1. **Regenerate organization manifests** whenever mapping configs change:
   ```bash
   python manage.py shell <<'PY'
   from arkumu.projects.services.schema_manifest_dataclass_generator import SchemaManifestDataclassGenerator
   generator = SchemaManifestDataclassGenerator()
   manifest = generator.load_manifest('rsh')  # repeat per org code
   with open('arkumu/projects/schema_manifest_model_rsh.py', 'w') as fh:
       fh.write(generator.build_module(manifest))
   PY
   ```
   Substitute the organization code (`rsh`, `fuk`, `det`, etc.) and destination file as needed. This reproduces the org-specific dataclasses tracked in `arkumu/projects/`.
2. **Canonical dataclasses refresh automatically** – import `arkumu.projects.schema_manifest_canonical` after regenerating the manifests; the module rebuilds its class definitions at import time from the updated files (no manual editing required).
3. **Run the adapter tests** to confirm round-tripping still works:
   ```bash
   docker compose -f docker-compose.local.yml run --rm django pytest arkumu/projects/tests/test_schema_adapters.py
   ```
4. **Update adapters when adding new organizations** by inserting the new manifest module into `ORG_MANIFEST_MODULES` inside `schema_manifest_canonical.py`; the adapters will start picking up bindings from the new module automatically.
- Relationship datasets such as `CanonicalActorEvent` (the actor/event join table) are generated automatically but marked with `expose_in_forms=False` for every field. Form builders should respect that flag to keep many-to-many joins hidden while adapters still populate the required linking rows behind the scenes.
- If you need an internal-only canonical class, you can skip adding it to `CORE_CANONICAL_CLASSES` and access it directly with `get_canonical_class(<canonical URI>)`; this keeps the entity out of end-user schemas while preserving adapter support.
- In `schema_manifest_canonical.py` relationship-only canonical classes (e.g., the actor/event join) have no entries in `FORM_VISIBLE_URIS`, so their fields remain hidden from end-user forms. The adapters still consume those classes to expand many-to-many rows into the organization-specific datasets.
